# v1.0.0dev 分支审查

日期：2026-10-27。分支 `v1.0.0dev`，相对 `origin/v1.0.0dev` 超前 50 个提交，工作区另有未提交的欢迎页权限改动。审查对象是当前工作区里的产品代码，包含已经在远端的分支历史，不只是那 50 个提交。

审查角度：桌面产品体验、运行时状态与架构、语音与文字流式、以及一次全分支缺陷扫描。高优先级条目都对照当前文件复核过。没有改代码。

## 范围和覆盖

全分支相对 `origin/main`（`5d20dbfb`）大约 440 个提交、1100 多个文件。缺陷扫描只读了其中 47 个文件，桌面主路径和 runtime 热路径大多不在那一批里。后面三次审查补上了这些面：

- 桌面：对话、任务、composer 模式、计划卡、审批、Computer Use、欢迎页权限（含未提交 diff）
- 运行时：`build.begin`、工作区、语音交接、Computer Use 批准、DeepSeek / 记忆默认值
- 流式：`text_preview`、caption 撤回、语音上下文

Flutter、Hub、记忆底物的大块历史没有逐文件看。下面没写到的区域，不代表没有问题。

## 结论

主对话、任务即对话、直接 Build、托管工作区、流式预览的成功路径是接上的。欢迎页在权限已授予时仍能打开系统设置，屏幕录制已授予时不再调用 `getSources`，和未提交测试一致。

还没接上的是几条用户会直接撞上的路径：Build 里开不了语音、审批入口会把审批界面藏起来、Computer Use 在绑定应用之后不再逐次询问、只配了 DashScope 的旧环境会被新的 DeepSeek 默认值把记忆抽取打到空密钥上。

## 高

### 1. Build 进行中无法进入语音，入口还会先停掉 Build

`clients/desktop/src/renderer/personal-controller.mjs:223`  
`runtime/src/personal-agent/host.ts:1913`

语音按钮先走 `guardBuildSwitch()`。Build 处于 `running` 或 `awaiting_approval` 时，宿主对 `conversations.voice` 直接返回 `build_stop_required`。离开工作台切到悬浮球也会走同一道门（`personal-controller.mjs:97`）。

10 月 26 日的模式契约要求任意模式都能切入实时对话，语音只澄清、不执行本地工具。Plan 已经能进语音；Build 被这道门挡住。用户在正在写代码的会话里点语音，得到的是“先停止 Build”。

### 2. “处理审批”会藏起唯一的批准界面

`clients/desktop/src/renderer/personal-view.mjs:185`  
`clients/desktop/src/renderer/workbench.css:273`  
`clients/desktop/src/renderer/approval-dock.mjs:22`

横幅按钮在选中会话之后调用 `setPresentation('orb')`。悬浮球模式把整个 workbench 设为 `display: none`，对话里的审批条一起消失。悬浮球自己的允许/拒绝依赖实时确认帧，不读快照里的 `pending_approvals`。重连之后，或某次批准从未变成悬浮球确认帧时，这条横幅会把仅剩的批准入口拿掉。

排队中的卡片两边按钮本来就是禁用的（`approval-dock.mjs:22`）。Build 进行中点这颗按钮，还会先撞上第 1 条的“离开工作台要停止 Build”。

### 3. 绑定应用之后，Computer Use 不再逐次批准

`runtime/src/personal-agent/workbench-runtime.ts:123-129`  
`runtime/src/executors/computer-device.ts:98` 与 `:206-208`  
`runtime/src/personal-agent/computer-use/contract.ts:22`  
`runtime/src/personal-agent/computer-use/skill.ts:8`

契约写明点击、输入、滚动、按键跟随 `local_tool_approval`。欢迎页文案也是“电脑操作仍需在 Nova 内逐次批准”。

实现里，`approve` 在 `applicationAuthorized` 为真时，对非 `Connect` 的动作直接放行。第一次带 `application` 的 `Connect` 被批准后，这个标志在当前 Computer Use 会话里一直为真。macOS 技能要求截图时带上应用名；`session.ts` 会先绑定该应用再 `Connect`。于是“允许连接这个应用”之后，同一次 Build 里后续的点击和输入不再弹批准。同意过的应用还会经 consent store 带到后面的回合（`:126`）。把确认开关拨回 Always ask，也恢复不了这些提示。

全屏、未绑定应用的路径仍然逐次询问。本地文件工具的 `ask` / `never` 也不走这个捷径。

### 4. 无障碍输入失败时，后台键入会激活目标窗口

`clients/desktop/native/macos_gui.swift:2`  
`clients/desktop/native/macos_gui.swift:19-31`  
`clients/desktop/native/macos_gui.swift:318` 与 `:338`

文件头约定后台输入不得把用户的应用调到前台。`focusRecord(..., active)` 在 `active == true` 时把 SkyLight 记录的激活字节设为 1。`Input` 的无障碍写入失败后，以及 `KeyboardPress` 的回退路径，都调用了 `focusRecord(pid, windowID, true)`。

这只发生在无障碍编辑失败之后，不是每次点击。和技能里“后台控制不得激活应用”的要求相反。技能后一句又建议用 `open -a` 启动或激活应用（`skill.ts:10`），模型侧和原生侧对“要不要抢前台”的说法也不一致。

### 5. 只配 DashScope 的环境，记忆抽取会打到 DeepSeek 且密钥为空

`runtime/src/config/config.ts:36`、`:40`、`:513-534`、`:623-627`  
`runtime/src/voicemem/store-worker.ts:120-122`  
`runtime/src/composition/cascaded-realtime-assembly.ts:435-439`

默认 `model_base_url` 和 `fast_model` 已改成 `https://api.deepseek.com` 与 `deepseek-flash`。本地记忆是否开启只看 embedding 密钥。DashScope 的 embedding 地址仍会用 `DASHSCOPE_API_KEY`，所以记忆模块显示为开。

抽取却始终用 `fast_model` 加上 `model_base_url`。`resolveModelApiKey` 只有在 URL 仍是 DashScope 时才取 `DASHSCOPE_API_KEY`。支持模型组装会改写 `support_model`，并在 `compressor_model` 仍是 `deepseek-flash` 时改写它，不改 `fast_model`，也不改抽取 URL。

结果：旧环境只设置了 `DASHSCOPE_API_KEY`、没有单独写 `FAST_MODEL` / `MODEL_BASE_URL` / `DEEPSEEK_API_KEY` 时，新对话会被记成待处理来源，抽取请求带着空密钥发往 DeepSeek，本进程内学不进去。已有记忆行不会被删。Embedding 连接本身是分开的，这点是对的。显式配了 DeepSeek 密钥的新安装不受这一条影响。

## 中

### 6. 已发布计划上再切到 Build，不会执行这份计划

`clients/desktop/src/renderer/composer-mode.mjs:45-49`  
`clients/desktop/src/renderer/workbench-agent.mjs:89` 与 `:102`

Composer 里的 Build 把会话模式改成 `chat`，并记下 `execution: 'build'`。计划卡只在 `mode === 'plan'` 时出现。下一条消息走 `build.begin`，新开一个没有计划的 Build。真正执行已发布计划的是计划卡上的“开始 Build”（`build.start`）。

从 Plan 按一次 Shift+Tab 就会掉进这条路。Delegate 预选执行器、计划卡上的内置 Build / 执行器分流，在计划已经发布且用户留在计划卡上时是对的。

### 7. 交给 Codex 时可以不选工作区

`clients/desktop/src/renderer/workbench-agent.mjs:50-62` 与 `:89`、`:111`

Codex 的目录列表第一项是空的“选择工作区”，也是初始值。“交给 codex”的禁用条件不要求选中目录。`plans.delegate` 只在 `directories.value` 非空时带上 `project`。空选会走宿主里“不指定项目”的旧路径，而不是内置 Build 那套托管工作区。

### 8. 执行器交接句会沉到更新的用户消息下面

`clients/desktop/src/renderer/chat-pane.mjs:38-54` 与 `:211`、`:287`  
`runtime/src/personal-agent/host.ts:616` 与 `:753`、`:811`

普通文字回复会插到对应那条用户消息后面（`:811`）。语音终稿和任务通知是 `push` 到数组末尾，`created_at` 用落盘时刻（`:616`、`:753`）。

直播 caption 先按 `seen_at` 夹在当时已有的消息之间，所以交接句在还是 caption 时位置是对的。同 `turn_id` 的持久消息一出现，caption 被删掉（`:287`）。主对话再按 `created_at` 排序（`:38`）；任务会话保持宿主数组顺序（`:211`）。相同文本、更晚时间戳的助手行还会让那条 caption 被去重丢掉（`:50`）。

用户在交接句还是直播气泡时又发了一条消息，落盘后会看到“交给 Codex”或任务结果跑到自己新消息的下面。这和 10 月 26 日测试记录第 4 条是同一类现象，直播阶段的修补没有保住落盘之后的顺序。

### 9. 展开悬浮球会把视线切回主对话，语音还留在任务上

`clients/desktop/src/renderer/personal-view.mjs:188` 与 `:200`  
`clients/desktop/src/renderer/personal-controller.mjs:198-199`

收到第一份带主对话的快照时会强制 `home()`。从悬浮球展开也会 `showHome()`，选中 `chat:main`。`select` 不停止语音。

从任务收成悬浮球再展开：左边是主对话，语音仍挂在刚才的任务上。启动时如果用户已经停在某个任务，第一次快照也会把它换成主对话。这次 `home()` 若和“新建任务”叠在一起，后到的 select 获胜，新任务会从眼前消失。

### 10. 关掉 Computer Use 会把整个 Build 暂停

`clients/desktop/src/renderer/computer-use-control.mjs:51`  
`runtime/src/personal-agent/host.ts:260`

开关只表示 Nova 不再操作电脑。宿主在 `enabled: false` 时调用 `stopLocalBuild`，Build 状态变成 `paused`。文件读写和 shell 一起停。

### 11. 计划或文字回复被中止后，预览气泡会留下

`runtime/src/personal-agent/workbench-runtime.ts:284` 与 `:295`  
`clients/desktop/src/renderer/chat-pane.mjs:281-289`

空的 `final` caption 能撤回预览，工具调用成功时也会发这颗撤回。中止信号到来时，工作台只在预览还活着且**没有**被 abort 时才发撤回；abort 分支直接返回“Build 已暂停。”，且不带 `turn_id`。

对话窗只在三种情况下删直播气泡：空 final、同 `turn_id` 的已落盘消息、Build 离开 `running` / `awaiting_approval`。Plan 会话的 kind 不是 `build`，第三种清不掉它。清空 Plan、或取消一次已经开始流出预览的文字回复，气泡会留在错误提示旁边。

Build 一旦变成 paused，这条气泡会被清掉。权威 `text_delta` 仍只在 `stop` 时发整段；预览不进工具历史；语音忽略 `text_preview`。成功路径的 `turn_id` 和落盘消息一致。

### 12. 进入 Plan 时，语音消息被整体接到上下文末尾

`runtime/src/personal-agent/workbench-runtime.ts:83-89`  
触发点：`runtime/src/personal-agent/host.ts:236` 切换到 Plan 会重置 checkpoint。

没有 checkpoint 时，先放入最近 32 条非语音消息，再把所有 `input_mode: 'voice'` 的消息接在后面，不按时间穿插。先语音、后切 Plan，较早的语音回合会变成模型看到的最新上下文。

已经有 checkpoint 的 Plan / Build 只追加新的语音消息，文字 → 语音 → 文字这条是对的。

### 13. 开语音时可能用上一拍的会话快照

`runtime/src/personal-agent/host.ts:928-929`  
`runtime/src/personal-agent/conversation-runtime.ts:251-256`

`conversations.voice` 先取出会话对象，再 await 公告收尾，以及可能停掉主对话上的语音，然后把**同一个对象**交给 `startVoice`。交接会丢掉 `generation_status: 'pending'` 的行。用户句要等回合结束才标完成，助手句也在 `runTurn` 之后才插入（`host.ts:806`、`:811`）。这两条队列独立，所以语音可以在文字回合刚写完、快照还是旧对象时启动。

语音侧会缺刚刚那一轮的用户句和回复。下一轮文字会重新读当前状态，所以文字模式还能看见。窗口只有那几次 await 那么长。现有的 Plan/Build 往返测试是等语音行已经在快照里才断言的，打不中这个窗口。

### 14. 本地工具确认开关可能和宿主相反

`clients/desktop/src/renderer/composer-approval.mjs:22-24` 与 `:35`  
`runtime/src/personal-agent/host.ts:231`

按钮用一个没有序号的 `localToolApproval()` 回读来设置文案。用户先点到 `never` 并写进宿主之后，迟到的回读会把按钮设回 `ask`。宿主仍是 `never`，下一次工具调用按宿主读。界面写着 Always ask，本地写入和命令已经自动放行。宿主切换本身不需要重启；错位只来自这次回读。窗口窄，但方向是危险的那一侧。

### 15. 批准详情加载失败时，只能拒绝、不能同意

`clients/desktop/src/renderer/workbench-agent.mjs:42` 与 `:100-101`  
`clients/desktop/src/renderer/chat-pane.mjs:252`

`build.approval` 存在时输入框禁用。同意按钮要等 `build.details` 完成且 `loadedApproval` 对上才启用。拒绝按钮立刻可点。详情请求失败时 catch 只写入错误文案，同意保持禁用。卡片还在，用户无法批准这次操作。

## 体验上还留着的一小处

主对话里的 feed 已经改成纯文本。带 `schedule_ref` 的消息仍会在气泡下画出“查看定时任务”和“查看任务”（`chat-pane.mjs:205`），这些行会进主对话收件箱（`host.ts:450`）。和“主对话少放按钮”的方向不一致，不影响主路径。

## 站得住的部分

- 左栏没有会话切换。任务页创建并选中会话。执行器输出在悬浮窗，不回到任务列表。
- 直接 Build 走 `build.begin`，`plan_id` 可选，缺省工作区解析到托管的 default。失败在写出消息、工具调用或运行中的回合之前会回滚。并发的第二个 Build 返回 `build_stop_required`。Resume 不要求已有计划。
- `workspace_id` 与任意 `project` 互斥。`workspaces.list` / `create` 不返回绝对路径。Codex 的 delegate 只接受 Codex 目录，占用时返回 `project_busy`，没有第二条工作区回退。ACP 被拒绝，而不是塞一个假目标。
- 同一时刻一个选中会话、一个语音所有者。Plan / Build 语音注入有界交接（摘要、最近 12 条、计划或 Build 状态），工具列表为空，伪造的工具调用以 `workbench_voice_readonly` 拒绝。语音行带回同一会话，下一轮文字以 `host_context` 注入一次。
- 带工具时，权威 `text_delta` 仍是 `finish_reason === 'stop'` 的一整段。预览不写入工具历史，随后的 `tool_call` 不把预览算进 `textSeen`，也不抛 `MixedResponseFailure`。文字模式按累计 `full_text` 补未发送的后缀。语音不开 `previewText`，TTS 只跟权威文本。
- Embedding 使用自己的 `EMBEDDING_BASE_URL`、`EMBEDDING_API_KEY`（DashScope 地址上才回退 DashScope 密钥）和 `text-embedding-v4`，不复用对话模型的 endpoint 或模型名。
- 未提交的欢迎页：已授予的麦克风、屏幕录制、辅助功能仍打开对应系统设置页；屏幕已授予时不调用 `getSources`。

## 建议的处理顺序

1. Computer Use 在 `ask` 下恢复逐次批准；连接应用和“始终允许此应用”不要变成后续点击的总开关。
2. 记忆抽取的密钥和 endpoint 跟 embedding 分开判断：只有 embedding 密钥时不要把抽取发到空的 DeepSeek。
3. Build 中的语音按契约放行，并且不要执行本地工具；不要用停 Build 来换语音。
4. “处理审批”留在工作台并打开审批条，不要切到悬浮球。
5. 交接句、任务结果按触发它的那条用户消息落位，而不是按落盘时刻追加到末尾。
6. 已发布计划上的 Composer Build 应走 `build.start`，或在切换时明确这是另起一个直接 Build。
